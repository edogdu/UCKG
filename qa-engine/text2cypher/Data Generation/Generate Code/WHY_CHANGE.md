# README: Why This New Pipeline?

## 1. The Problem: From Raw LLM Output to a Valid Dataset

Getting from a raw list of questions and Cypher queries generated by an LLM to a high-quality, trustworthy, and useful dataset is a major challenge. The raw data is often plagued with hidden errors that are impossible to catch manually.

### Problem 1: Duplicate Data
An LLM may generate the same question/query pair multiple times, which can bias training and analysis.

### Problem 2: Tedious Manual Labor
A useful dataset needs more than just a question and query. You need to know what schema elements are used, how complex the query is (*hops*), and what specific values are being searched for.  
Manually creating these “helper” columns (`ExpectedNodeLabels`, `Hops`, etc.) is incredibly slow and prone to human error.

### Problem 3: Schema Hallucination
The LLM might invent labels, relationships, or properties that don’t exist in our graph (e.g., generating `:CVE` instead of `:UcoCVE`).

### Problem 4: Syntax Errors
The generated Cypher might simply be invalid and won’t run on the database.

### Problem 5: Semantic Irrelevance
The query might be syntactically perfect and use the correct schema but fail to actually answer the question.  
This is a very common failure mode.

### Problem 6: Value Hallucination
This is the most subtle error. The query is perfect in every way, except it searches for the **wrong value**.

**Example:**

- **Question:** “Find info on 'CVE-2021-44228'.”  
- **Query:**  
  ```cypher
  MATCH (c:UcoCVE {label: 'CVE-2025-12345'}) RETURN c
  ```
This query would pass all traditional checks (schema, syntax, relevance) but is factually wrong.

---

## 2. The Solution: A Complete "Process-and-Validate" Pipeline

The new script is no longer just a “validator.”  
It’s an **automated enrichment and validation pipeline** that solves every one of these problems in a specific order.

---

### Step 1: Solving the Duplicate Problem (Gatekeeper)

- **Function:** `check_for_initial_duplicates()`

**What it Does:**  
Acts as a gatekeeper. It performs a strict check for duplicate `(Question, Cypher)` pairs.  
If any are found, it logs them and halts execution so you can clean the raw data without wasting time.

---

### Step 2: Solving the Manual Labor Problem (Enrichment)

- **Function:** `enrich_dataset()`

**What it Does:**  
Once the data is confirmed to be unique, this function automatically parses every Cypher query and generates all the helper columns for you.  
This saves countless hours of manual work and ensures 100% consistency.

**It populates:**
- `ExpectedNodeLabels`
- `ExpectedRelationshipTypes`
- `ExpectedProperties`
- `Hops` *(query complexity)*
- `ExtractedPropertyValues` *(critical for solving Problem 6)*

---

### Step 3: Solving All "Hidden Errors" (Validation)

After the data is fully enriched, the script runs a **comprehensive five-stage validation suite**, with each stage logging to its own file.

| **Validation Function** | **Problem Solved** | **Description** |
|--------------------------|--------------------|-----------------|
| `validate_schema_elements` | Problem 3 | Checks that the query’s nodes, relationships, and properties exist in `schema_cache.txt`. |
| `validate_query_executability` | Problem 4 | Runs the query (with `LIMIT 1`) against the live Neo4j database to ensure it executes. |
| `validate_semantic_relevance` | Problem 5 | Uses a Sentence Transformer to verify that the question and query have matching meaning. |
| `validate_extracted_values_in_question` | Problem 6 | Checks that literal values in the query match the question text (ignores common values like `true`, `false`, `1`; supports partial matches like “SolarWinds” ↔ “SolarWinds Orion Attack”). |
| `validate_expected_entities_match_query` | — | Sanity check that confirms enrichment worked correctly. |

---

## Better Logging for Better Debugging

This entire process logs its findings to **six separate files**, making debugging incredibly efficient.

| **Log File** | **Purpose** |
|---------------|-------------|
| `duplication_check.txt` | Shows any raw data you need to delete. |
| `schema_check.txt` | Lists all queries with hallucinated schema. |
| `cypher_check.txt` | Lists all queries that failed to execute. |
| `relevance_check.txt` | Lists all queries that don’t semantically match their question. |
| `value_check.txt` | Lists all queries that search for the wrong data (value hallucination). |
| `entity_check.txt` | Confirms the enrichment step is working as expected. |
